# Аудит перед этапом 0

Аудит выполнен относительно состояния `main` перед внедрением миграций.

## Обнаруженные расхождения

- Схема SQLite создавалась одним блоком SQL и двумя условными `ALTER TABLE`.
  Версия схемы и история применённых изменений не сохранялись.
- Перед изменением существующей базы не создавалась согласованная резервная
  копия. Это особенно рискованно для SQLite в режиме WAL.
- Контекст `Database.connect()` выполнял `commit` даже при исключении внутри
  транзакции. Частично выполненная опасная операция могла сохраниться.
- Таблица `jobs` описывала только анализ фотографий и не содержала общего типа
  фоновой задачи или расширяемой нагрузки.
- Тесты базы проверяли только настройки. Не проверялись миграция существующих
  данных, резервная копия, обратимость и откат транзакции.
- Тесты `Storage` покрывали основные успешные сценарии, но не проверяли
  междисковый перенос, несовпадение контрольной суммы и конфликт карантина.
- API-тесты фиксировали только health, вход и пустую сводку. Ключевые сценарии
  сортировки — папки, перенос, решение проверки и подтверждение удаления — не
  были защищены регрессионными тестами.

## Решение этапа 0

- Схема разбита на последовательные миграции с `PRAGMA user_version` и таблицей
  `schema_migrations`.
- Старые базы без номера версии распознаются по фактической структуре.
- Перед автоматическим обновлением существующей базы создаётся и проверяется
  SQLite backup в каталоге `PHOTO_REVIEW_DATA/backups`.
- Каждая миграция выполняется в одной транзакции и имеет обратное действие.
- В `jobs` добавлены `kind` и `payload`; прежние строки получают тип `analysis`.
- Транзакции базы теперь откатываются при исключении.
- Добавлены защитные тесты миграций, Storage и основных API сортировки.

Интерфейс, маршруты и пользовательский процесс раздела «Сортировка» не
изменены. Этап 1 не начинался.
